# Аудит документа по чанкам

## Зачем чанки

Целый документ модель просматривает поверхностно: на 500 страницах она сообщает
долю того, что там есть. Чанк заставляет вчитываться в каждую строку — на том же
документе это даёт кратно больше находок. Размер чанка задаётся в `docs-ai-prep`
и по умолчанию 48 000 токенов; рабочий диапазон 32 000–64 000, до 128 000 при
необходимости. Больше — начинает теряться середина.

## Перед началом

Рабочая папка должна быть создана скиллом `docs-ai-prep`. Если её нет — сначала
он. В папке лежат `manifest.json`, `block_map.json`, `render_map.json`,
`chunks/chunk_NNN.md` и пустая `findings/`.

Правила аудита — в `rules/audit_rules.md` рядом с этим файлом. **Прочитай их
целиком перед первым чанком.** Если пользователь дал свой файл правил —
используй его вместо этого.

## Процесс

1. Посмотри объём работы:

```bash
"<skill>/scripts/run.cmd" dispatch.py status --work "<work_dir>"
```

2. Возьми очередные чанки:

```bash
"<skill>/scripts/run.cmd" dispatch.py next --work "<work_dir>" --count 5
```

3. Для каждого чанка: прочитай файл целиком, найди ошибки по правилам, запиши
   `findings/<chunk_id>.json`. Один чанк — один файл, ничего не накапливай в
   голове и не откладывай запись на потом.

4. Когда все чанки закрыты — проверь себя:

```bash
"<skill>/scripts/run.cmd" dispatch.py validate --work "<work_dir>"
```

Диспетчер вернёт ненулевой код, пока есть непроверенные чанки или битые находки.
**Не сообщай пользователю, что аудит закончен, пока `status` не скажет
`complete`.** Это единственная защита от того, что часть документа осталась
непрочитанной — в отличие от цикла в программе, агент способен незаметно
пропустить кусок.

## Кому какой чанк: читай задание из манифеста

Решение уже принято на этапе подготовки. У каждого чанка в `manifest.json` есть
готовые поля — **не выбирай модель сам, исполняй назначенное**:

```json
{ "id": "chunk_007", "profile": "deep", "role": "analyst", "model": "sonnet",
  "effort": "high", "reasons": ["tables 100% of blocks", "numbered run of 8"] }
```

- `role` — `reader` (быстрый чтец) или `analyst` (рассуждающий). Это главное:
  роль не зависит от платформы.
- `model` — конкретная модель для платформы, выбранной при подготовке. Если ты
  работаешь не на ней (например, манифест готовили под `codex`, а исполняешь ты
  в Claude Code) — бери свой эквивалент той же роли: reader → haiku,
  analyst → sonnet.
- `effort` — `low` / `medium` / `high`, укажи субагенту, насколько тщательно
  считать и сопоставлять.
- `reasons` — почему чанк отнесён к глубокой проверке; вставь в задание, чтобы
  субагент знал, на что смотреть.

Назначение зависит от пресета, который пользователь выбрал при подготовке
(`scan` / `standard` / `deep`), и от состава чанка. Если пользователь просит
проверить тщательнее — не меняй модель на ходу, а предложи перезапустить
подготовку с другим пресетом: вместе с моделью изменится и нарезка.

## Глубина проверки: профиль чанка

В документе живут два разных класса ошибок, и они требуют разного внимания.

**Формальные** — опечатки, пробелы, кавычки, сокращения, единицы, согласование
оборотов. Это сверка с образцом: модель видит их сразу, размышление почти ничего
не добавляет.

**Смысловые** — сумма граф не сходится с итогом, население города в миллиард
человек, в ряду 112, 113, 115 пропущен 114, одна и та же строка задвоена, статус
объекта противоречит соседнему разделу. Здесь надо удерживать значения рядом и
сравнивать — вот на это рассуждение и тратится.

`docs-ai-prep` заранее размечает каждый чанк в манифесте полем `profile`:

- **`light`** — сплошной текст. Бери **Haiku, низкое усилие**. Высокий reasoning
  здесь не поможет: он породит не находки, а гипотезы «ПРОВЕРКА: возможно...».
- **`deep`** — таблицы, плотные числа, нумерованные ряды. Бери **Sonnet, высокое
  усилие**. В `reasons` записано, почему чанк отнесён сюда.

Если находок в light-чанке подозрительно мало — поднимай не глубину рассуждения,
а дроби мельче: перезапусти подготовку с `--chunk-tokens 24000`. Внимание в этой
задаче регулируется объёмом текста перед глазами, а не бюджетом на размышления.

**Эскалация.** Если субагент на light-чанке сообщает, что наткнулся на числовую
таблицу и не уверен в расчётах, — отдай этот же чанк Sonnet с высоким усилием
повторно, перезаписав файл находок.

## Выдуманные цитаты

Быстрая модель на большом чанке иногда пересказывает цитату вместо того, чтобы
привести её дословно. Такая находка выглядит как настоящая, но по ней нельзя ни
поставить якорь, ни проверить факт. `validate` ловит это автоматически, сверяя
каждую `quote` и каждый `old_text` с текстом чанка. Если проверка ругается —
верни чанк субагенту на переделку с требованием цитировать буквально; не
исправляй цитаты сам, ты не видел текста его глазами.

## Параллельная работа

Чанки независимы, перекрытие уже вшито в текст. Раздавай их субагентам пачками
по 4–8 — каждый читает свой чанк и пишет свой файл находок. Модель выбирай по
профилю чанка, как описано выше. Opus не нужен ни там, ни там.

В задании субагенту дай: путь к чанку, путь к правилам, путь к файлу находок и
контракт ниже. Ничего больше ему знать не требуется.

## Контракт находки

`findings/<chunk_id>.json` — объект с массивом `findings` (пустой массив, если
ошибок нет, — это нормальный ответ, файл всё равно создай):

```json
{
  "chunk_id": "chunk_003",
  "findings": [
    {
      "block_id": "docx_tbl_0022_r011_c002_p001",
      "quote": "неорганическая:70-20%",
      "violation": "Отсутствует пробел после двоеточия",
      "fix": "Добавить пробел после двоеточия",
      "fix_mode": "safe_replace",
      "old_text": "неорганическая:70-20%",
      "new_text": "неорганическая: 70-20%",
      "confidence": "high"
    }
  ]
}
```

Обязательные поля: `block_id`, `quote`, `violation`, `fix`, `fix_mode`,
`confidence`.

- `block_id` — строго из заголовка `[BLOCK:...]` того блока, где ошибка. Выдуманный
  id находку убьёт: она не попадёт в отчёт.
- `quote` — **дословный** фрагмент из текста чанка, не пересказ. По нему находка
  проверяется и по нему же ставится якорь в документе.
- `violation` и `fix` — по-русски, коротко, без английских вставок.
- `fix_mode` — `safe_replace`, если можешь дать точную замену, иначе
  `requires_review`.
- `old_text` / `new_text` — обязательны при `safe_replace`, и они должны
  различаться. Замена применяется механически, поэтому `old_text` должен
  встречаться в блоке дословно.
- `confidence` — `high` / `medium` / `low`.

Если находка требует сверки с другими местами документа (не сходятся суммы,
противоречат друг другу цифры, разное написание одного названия) — ставь
`requires_review` и начинай `violation` со слова `ПРОВЕРКА:`.

## Что не считать ошибкой

Полный перечень — в правилах, но чаще всего лишние замечания дают эти места:

- Выбор между дефисом, тире и минусом. Знаки взаимозаменяемы, замену не предлагай.
- Регистр в названиях улиц и адресных объектов.
- Инициалы без пробела: `И.И. Иванов` — принятая форма.
- Прочерк в пустой графе таблицы и тире между графами.
- Расхождения итогов в пределах округления (0,01).
- Пробел как разделитель разрядов: `153 220,95` — норма.
- Объединённые ячейки, многоуровневые шапки, чередование уровней нумерации.
- Реестровые номера, кадастровые номера, номера НПА и ГОСТов — сохраняй как в
  источнике, формат не «улучшай».
